# Codex 项目协作规则与锚点总文档

这份文档是 Codex 后续执行项目任务前必须阅读的项目规则文档。

它的作用是：

1. 防止 Codex 误解项目阶段。
2. 防止 Codex 擅自改代码。
3. 防止旧版本锚点污染新版本。
4. 防止 UI、题库、评分、人格、故事线互相脱节。
5. 保证所有开发都围绕已确认锚点推进。
6. 保证每次任务都先报告、再确认、再执行。
7. 保证心岛、小红书等不同项目不要混淆。

Codex 没有长期稳定记忆，因此每次新任务开始前，都应该优先阅读本规则文档和当前任务指定的最新锚点报告。

## 1. 总协作原则

### 1.1 默认收敛，不默认发散

除非用户明确要求 brainstorm、发散、多方案探索，否则默认进入收敛模式。

不要在已有项目锚点之外随意新增方向、功能、系统或复杂规划。

### 1.2 新项目必须先讨论，再研究，再规划，再开发

任何新项目不能直接写 PRD、直接写代码、直接出页面。

默认流程：

```text
讨论想法 -> 研究同类产品/竞品/方法 -> 确认项目锚点 -> 出项目方案 -> 用户确认 -> 再进入开发
```

### 1.3 项目锚点优先

一旦某个项目锚点被确认，后续版本必须围绕锚点推进。

重大方向变化必须先重新讨论，并生成新的锚点文档。不要在执行中擅自改变产品目标。

### 1.4 先方案，后代码

涉及核心结构变化时，必须先输出方案报告，不直接修改代码。

尤其包括：

| 类型 | 规则 |
| --- | --- |
| 测评框架 | 先出方案，不直接改题库或评分。 |
| 题库 | 先出题库规则、蓝图、审计标准。 |
| 评分系统 | 先出评分架构和验证方案。 |
| 人格矩阵 | 先出人格候选、构念锚点、targetVector 规则。 |
| 结果页结构 | 先确认信息层级，再改 UI。 |
| 商业流程 | 先确认转化目标和合规边界。 |
| 自动化流程 | 先确认平台规则和风险边界。 |
| 发布逻辑 | 先确认权威入口和部署路径。 |
| 数据结构 | 先确认字段、来源、用途和迁移影响。 |

### 1.5 用户是最终决策者

ChatGPT / Codex 可以分析、评审、提出建议，但最终决策由用户确认。

Codex 不要把建议当成已经确认的决策。

### 1.6 3-6 个月实用优先

用户当前需要的是未来 3-6 个月能坚持推进、能落地、能帮助变现或作品集积累的产品流程。

不要把项目包装成宏大的长期方法论，优先输出可执行、可验证、可迭代的方案。

### 1.7 主动发现风险

每次方案都要主动指出：

1. 可能失败的地方。
2. 最大风险。
3. 当前最不应该做什么。
4. 是否偏离变现、作品集或落地目标。
5. 是否过度开发。

## 2. Codex 执行流程规则

### 2.1 执行前确认项目

每次任务开始前，先确认当前打开的项目目录是否正确。

如果用户指定的是心岛项目，必须确认当前目录是心岛项目，而不是其他项目。如果目录不确定，先报告，不要修改任何文件。

### 2.2 默认先读文档

每次任务开始前，优先阅读：

1. `docs/CODEX_PROJECT_RULES_AND_WORKFLOW.md`
2. 当前任务指定的最新报告
3. 相关历史报告
4. 当前代码文件

不要只根据用户一句话就直接改代码。

### 2.3 只做当前任务

不要顺手修复其他问题。

不要“看到问题就顺手改”。

不要扩大任务范围。

### 2.4 有改动必须可追溯

如果进入代码修改阶段，必须说明：

1. 修改了哪些文件。
2. 为什么修改。
3. 是否影响题库。
4. 是否影响评分。
5. 是否影响人格。
6. 是否影响 UI。
7. 是否影响部署。
8. 是否需要重新跑测试。

### 2.5 报告优先

每一阶段都应该产出报告。

报告放入 `reports/` 目录。报告命名要清晰，优先包含项目名、版本号、任务名、`report` / `plan` / `audit` / `qa` 等后缀。

### 2.6 测试优先

涉及代码修改时，必须按项目实际情况运行相关测试，例如：

```bash
npm test
npm run check
npm run build
```

也包括项目已有审计脚本、Playwright / E2E 检查等。

如果测试不能运行，要在报告里说明原因。

### 2.7 不允许静默失败

如果某个命令失败、文件不存在、路径不一致、依赖缺失，必须报告。

不要假装完成。

## 3. 心岛项目长期规则

### 3.1 项目定位

心岛计划 / Heart Island 是一个恋爱人格测试产品。

当前方向不是临床心理诊断，而是：

> 参考亲密关系心理学框架，帮助用户理解自己在亲密关系中的模式。

禁止宣传为：

1. 专业心理诊断。
2. 科学诊断恋爱人格。
3. 判断心理问题。
4. 临床量表。

允许表达为：

1. 恋爱人格测试。
2. 亲密关系模式探索。
3. 自我理解。
4. 情感反思。
5. 参考亲密关系心理学框架。

### 3.2 心岛 v1.0 旧锚点

旧阶段曾以以下内容为主要锚点：

1. 12 维度。
2. 12 核心人格。
3. 36 题。
4. Beta 0.9.9.x。
5. 移动端 H5。
6. 可公开测试、可分享、可作品集展示。

这些旧锚点现在只能作为历史素材，不再自动作为 v2.0 标准。

### 3.3 心岛 v2.0 新锚点

心岛 v2.0 当前新方向是：

> 以五层亲密关系构念为底层结构，以 15 构念和 60 题为准确性优先方案，重建题库、评分、人格式矩阵、结果解析和轻叙事做题流程。

当前建议框架：

#### 第一层：依恋与安全系统

1. 安全确认
2. 自主边界
3. 关系信任

#### 第二层：爱情成分系统

4. 亲密连接
5. 激情启动
6. 承诺经营

#### 第三层：爱情风格系统

7. 灵魂理想
8. 新鲜探索
9. 现实匹配
10. 照顾支持

#### 第四层：关系运转系统

11. 表达沟通
12. 冲突修复
13. 情绪调节

#### 第五层：关系维持与叙事系统

14. 关系投入 / 留下倾向
15. 回忆牵引 / 关系叙事

### 3.4 心岛 v2.0 题量规则

当前推荐：

```text
15 构念 x 每构念 4 题 = 60 题
```

准确性优先，不要为了压缩到 36 题而牺牲构念清晰度。

每个构念 4 题可包含：

1. 核心倾向题。
2. 真实关系场景题。
3. 压力 / 冲突场景题。
4. 反向 / 边界题。

用户端不展示题型，不连续暴露同一构念，避免用户察觉测试意图和表演式作答。

### 3.5 心岛 v2.0 题库规则

题库必须遵守：

1. 每题只测一个主构念。
2. 不要双句绑定。
3. 不要明显正确答案。
4. 不要把高分写成好人，低分写成坏人。
5. 不要把健康边界误判为低照顾。
6. 不要把自由需求写成逃避责任。
7. 不要把修复能力写成单方面忍让。
8. 不要把情绪调节写成玄学感应。
9. 不要为了故事线牺牲测评准确性。

### 3.6 心岛 v2.0 评分规则

题库和评分必须强绑定。

链路必须是：

```text
题目 -> 选项分值 -> 构念分 -> 人格向量匹配 -> 主性人格 -> 白话解析素材 -> 结果页
```

每题必须能追溯到：

1. 构念。
2. 题型。
3. 分值。
4. 是否反向。
5. 影响哪个构念。
6. 是否用于人格区分。
7. 是否用于结果解析。

禁止：

1. 凭氛围写题。
2. 凭氛围写人格。
3. 凭氛围写结果文案。
4. 先写题库后硬接评分。
5. 先定人格后强行扭曲构念。

### 3.7 心岛 v2.0 人格规则

旧 12 人格可以：

1. 保留。
2. 改名。
3. 合并。
4. 删除。
5. 新增。

不要为了保留旧 12 人格而扭曲题库。

人格是输出层，不是底层理论。主性人格应由 15 构念组合自然生成。

建议主性人格数量控制在 12-16 个。不建议做 30+ 复合人格，避免评分、文案、分享、拟人图失控。

### 3.8 心岛 v2.0 结果展示规则

用户端只展示一个主性人格。

禁止展示：

1. 副导。
2. 副岛。
3. 副人格。
4. Top2。
5. 张力潮汐。
6. 构念雷达。
7. 15 维得分表。
8. 复杂心理术语。

内部可以计算：

1. 第二匹配人格。
2. 高分构念。
3. 低分构念。
4. 构念组合。
5. 近邻人格。
6. 构念冲突。
7. 置信度。

但这些只能转成白话解析，不作为标签展示。

### 3.9 心岛 v2.0 故事线规则

故事线采用轻叙事，不采用强剧情。

推荐方式：

```text
心岛轻叙事 + 真实关系场景
```

故事线是氛围外壳，题目测的必须是真实关系行为。

禁止：

1. 强 RPG。
2. 冒险任务式剧情。
3. 纯诗意隐喻。
4. 纯普通心理问卷。
5. 因为贴合海岛故事而让题目变模糊。

### 3.10 心岛 v2.0 当前执行路线

后续顺序必须是：

```text
规则文档同步
-> 构念定稿
-> 主性人格矩阵
-> 题库与评分架构
-> 60 题候选题库
-> 题库审计
-> 评分系统落地
-> 结果文案重写
-> UI / 代码实现
-> 测试与部署
```

不要跳过前面的结构阶段直接改代码。

## 4. 小红书项目规则

### 4.1 项目方向

用户的小红书项目不应盲目追求全自动无人发布。

更稳的方向是：

> 半自动内容生产与发布助手。

### 4.2 风控边界

不要和小红书平台风控硬碰。

不要把重点放在绕过验证码、绕过检测、全自动发布、模拟真人发布上。

更合理方向：

```text
AI 内容生成 -> 人工编辑 -> 配图/封面辅助 -> 一键复制/半自动填充 -> 用户自己确认发布
```

### 4.3 内容质量优先

用户已经明确不满意普通 AI 文案，因为常见问题包括：

1. AI 味重。
2. 不敢说。
3. 生硬。
4. 信息不全。
5. 不贴合发布人真实意图。
6. 缺少真实小红书语气。
7. 模板感明显。

所以小红书项目重点不是自动发布，而是：

1. 文案质量。
2. 垂直领域真实感。
3. 低 AI 味。
4. 低模板感。
5. 转化引导。
6. 适配真实发布者。

### 4.4 产品方向约束

小红书项目未来应优先围绕：

1. 垂直领域。
2. 案例驱动。
3. 真实语气。
4. 人工审核。
5. 半自动提效。
6. 商业验证。

不要一开始做成大而全内容中台。

## 5. 项目协作阶段规则

### 5.1 Research 阶段

用途：

1. 研究问题。
2. 对比竞品。
3. 参考成熟框架。
4. 确定是否值得做。

输出：

1. 研究报告。
2. 竞品对照。
3. 风险判断。
4. 是否继续建议。

禁止：

1. 直接写代码。
2. 直接设计 UI。
3. 直接扩功能。

### 5.2 Strategy 阶段

用途：

1. 确定项目锚点。
2. 确定产品方案。
3. 确定版本路线。
4. 确定边界和禁止事项。

输出：

1. 项目方案。
2. 版本计划。
3. 规则文档。
4. 决策表。

禁止：

1. 未确认就开发。
2. 边讨论边改代码。

### 5.3 Development 阶段

用途：

1. 按确认后的方案实现。
2. 写代码。
3. 跑测试。
4. 生成验收报告。

输出：

1. 代码改动。
2. 测试结果。
3. 验收报告。
4. commit 建议。

禁止：

1. 开发时擅自改方向。
2. 顺手加功能。
3. 不跑测试就报告完成。

## 6. 版本与报告规则

### 6.1 报告路径

所有阶段性报告放入：

```text
reports/
```

### 6.2 文档路径

长期规则、项目记忆、协作规范放入：

```text
docs/
```

### 6.3 命名规则

报告命名要清晰，优先包含：

1. 项目名。
2. 版本号。
3. 任务名。
4. `report` / `plan` / `audit` / `qa` 等后缀。

### 6.4 每轮报告必须说明

1. 本轮目标。
2. 是否改动代码。
3. 改动文件。
4. 关键结论。
5. 风险。
6. 下一步。
7. 是否需要用户确认。

### 6.5 如果没有改代码

必须明确写：

> 本轮没有改动代码。

## 7. Codex 禁止事项总表

| 禁止事项 | 原因 |
| --- | --- |
| 未确认方案直接改代码 | 容易跑偏。 |
| 顺手修复无关问题 | 破坏任务边界。 |
| 为了旧人格扭曲新构念 | v2.0 已进入新框架。 |
| 为了题量短合并多个构念 | 影响准确性。 |
| 用户端展示副导 / Top2 / 雷达 | 产品复杂化，削弱主结果记忆点。 |
| 强剧情绑架题目 | 降低测评准确性。 |
| 全自动绕平台风控 | 风险高且偏离产品价值。 |
| 把心岛说成专业诊断 | 不符合产品边界。 |
| 把小红书项目重点放在自动发布 | 当前核心是内容质量。 |
| 在 Strategy 阶段擅自开发 | 阶段错位。 |
| 在 Development 阶段擅自扩展功能 | 破坏已确认范围。 |
| 命令失败后假装完成 | 不可追溯。 |
| 改题库但不说明评分影响 | 题库和评分必须强绑定。 |
| 改 UI 但不验证移动端 | 心岛是移动端 H5 产品。 |

## 8. Codex 每次任务前自检清单

每次 Codex 开始任务前都要检查：

1. 我当前在哪个项目？
2. 当前任务属于 Research、Strategy 还是 Development？
3. 用户是否明确允许改代码？
4. 最新项目锚点是哪份报告？
5. 本轮是否只应该输出报告？
6. 是否涉及题库 / 评分 / 人格 / UI / 部署？
7. 如果涉及心岛，是否符合 v2.0 新锚点？
8. 如果涉及小红书，是否符合半自动、内容质量优先方向？
9. 是否有禁止事项？
10. 本轮完成后是否需要报告“是否改动代码”？

如果以上任一项不清楚，应先报告或澄清，不要擅自修改文件。
