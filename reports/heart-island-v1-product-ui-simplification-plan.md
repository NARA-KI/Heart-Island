# 心岛计划 v1.0 产品目标与 UI 简化改造方案

## 1. 总结结论

心岛计划当前不是从零开始的项目，而是一个已经具备基础能力的 H5 恋爱人格测试产品。根据 `reports/heart-island-full-audit-report.md`，项目已经拥有 36 道题、12 核心人格主结果、完整做题流程、结果页 Hero、12 人格拟人图、12 人格图标、12 地点场景图、分享图生成基础和评分审计脚本基础。

v1.0 的重点不是扩功能，而是收敛、简化、稳定、可传播。当前最应优先解决的是移动端首页首屏 CTA、版本发布权威源、评分审计口径、12 核心人格边界和结果页分享链路。

本方案只定义产品与 UI 改造方向，不修改任何代码、题库、评分参数、文案、样式或视觉资源。

## 2. 当前项目状态判断

| 维度 | 当前状态 | v1.0 判断 |
| --- | --- | --- |
| 版本 | 根目录更接近 `Beta 0.9.9.4 RC`，不是 0.9.9.5/0.9.9.6 | 需要统一版本口径 |
| 主流程 | 首页、做题、结尾、结果、分享均已存在 | 具备 v1.0 基础 |
| 题库 | 36 题连续完整，每题 4 选项 | 不建议重写 |
| 人格体系 | 前台主结果为 12 核心，代码仍保留 8 分支 | 需要设置边界 |
| 评分 | calibrationB 参数一致，但审计默认 profile 易误导 | 需要统一检查命令 |
| 首页 | 移动端首屏看不到开始按钮 | P0 修复 |
| 做题页 | 场景图可见，选项可点，但视觉占屏偏重 | 需要简化 |
| 结果页 | Hero 有主人格、拟人图、匹配度、关键词、分享入口 | 需要强化传播入口 |
| 分享卡 | Canvas 基础存在 | 需要真机保存验证 |
| 测试脚本 | 有审计脚本，但无统一 `npm test/check/e2e` | 需要标准化 |

当前项目可以进入 v1.0 收敛阶段，但不应继续增加复杂世界观、人格数量、后端能力或大规模动画。

## 3. v1.0 产品锚点

心岛计划 v1.0 的目标不是做一个复杂 App，也不是做心理咨询产品，而是：

**把现有心岛从“可运行的恋爱人格测试 Demo”，打磨成一个可以公开测试、可以分享传播、可以放进作品集展示的沉浸式恋爱人格 H5 产品。**

v1.0 三大目标：

| 目标 | 定义 | 验收标准 |
| --- | --- | --- |
| 公开测试 | 陌生用户打开链接后，不需要解释，就能在手机上顺畅完成测试 | 首页 3 秒内理解，开始按钮首屏可见，36 题可完成 |
| 分享传播 | 用户得到结果后，愿意保存自己的心岛人格卡并发给朋友或社交平台 | 结果页首屏有分享入口，分享卡可保存，视觉值得转发 |
| 作品集展示 | 项目能体现产品定位、AI 协作开发、视觉整合、移动端体验和验收意识 | README、报告、截图、测试命令和发布版本清晰 |

v1.0 的产品一句话可以收敛为：

> 36 道心岛旅程题，生成你的 12 核心恋爱人格身份卡。

## 4. v1.0 不做事项

为了防止项目发散，v1.0 前明确不做：

- 不做登录注册。
- 不做数据库。
- 不做用户系统。
- 不做付费系统。
- 不做后台管理。
- 不做 App 化。
- 不接 AI 实时生成结果。
- 不新增人格。
- 不回归 20 类型主结果。
- 不重写整套题库。
- 不大规模重构 `app.js`。
- 不做复杂动画大片感。
- 不更换整套视觉风格。
- 不引入新框架。

本阶段重点是：**收敛、简化、稳定、可传播。**

## 5. 官方 12 核心人格边界

v1.0 前台主结果只允许使用以下 12 个核心人格：

1. 灯塔型
2. 守门人型
3. 筑巢型
4. 收藏家型
5. 候鸟型
6. 岛屿型
7. 探险家型
8. 流浪诗人型
9. 星火型
10. 月光型
11. 镜像型
12. 观星者型

边界规则：

| 使用场景 | 允许范围 |
| --- | --- |
| 前台主人格结果 | 只能使用 12 核心人格 |
| 结果页 Hero | 只能展示 12 核心人格 |
| 分享卡 | 只能使用 12 核心人格 |
| 结果页 Top5 | 只能从 12 核心人格中产生 |
| 旧 8 分支人格 | 可作为历史兼容、图鉴彩蛋或归档，但不能混入主结果 |
| 审计脚本 | 可以保留全 20 类型调试能力，但默认口径必须明确 |

后续代码修改时，需要防止误用全 20 类型池。任何新功能只要涉及“主结果、分享、Hero、用户可见人格名”，都应优先确认数据来源是否为 12 核心池。

## 6. 最终用户路径

| 步骤 | 用户目标 | 当前基础 | v1.0 状态判断 | 处理建议 |
| --- | --- | --- | --- | --- |
| 首页 | 看到产品名、核心说明和开始按钮 | 已有标题、说明、按钮、氛围背景 | 需要修复 | CTA 首屏必须可见 |
| 做题页 | 完成 36 题，感到轻量航行感 | 已有 36 题、进度、场景图、上一题 | 需要简化 | 题目和选项优先，场景弱化 |
| 结尾过渡页 | 答完题后感到“抵达心岛” | 已有结尾页、湖面、光点、小岛轮廓 | 已具备，需简化 | 保留短仪式感，控制时长 |
| 结果页 | 看到 12 核心人格、拟人图、匹配度、关键词、命中句 | 已有 Hero 和折叠内容 | 需要简化 | 首屏聚焦身份卡 |
| 分享卡 | 生成并保存结果卡 | 已有 Canvas 生成基础 | 需要验证 | 优先真机保存和视觉验收 |
| 反馈/复测 | 提供反馈或重新测试 | 已有反馈和复测入口 | 已具备 | 保持低权重，不抢主流程 |

v1.0 用户路径应保持单线：进入、开始、答题、抵达、认领身份、保存分享、反馈或复测。

## 7. UI 简化总原则

心岛 v1.0 的 UI 不再追求“每个页面都展示复杂插画和完整世界观”，而是追求：

**一屏一个重点，一页一个行动，一个结果一个记忆点。**

视觉从“多图、多层、多氛围”收敛为：

- 深海渐变。
- 星点。
- 航线。
- 小岛轮廓。
- 轻微玻璃质感卡片。
- 少量雾气。
- 12 人格拟人图只在结果页和分享卡重点出现。

不要再让每张场景图都抢戏。场景图在做题页的作用是提供轻量氛围，不是成为主角。主角应当是题目、选项、结果身份和分享卡。

## 8. 视觉风格关键词

v1.0 视觉风格关键词：

- 深海蓝
- 冷白星光
- 雾面玻璃
- 极简线条
- 小岛剪影
- 航海图感
- 安静
- 神秘
- 克制
- 高级感

需要避免：

- 大量彩色插画堆叠。
- 卡通可爱。
- 粉色情侣 App 风。
- 游戏 UI / RPG 冒险感。
- 普通心理测试网页模板。
- 过度 3D。
- 过度梦幻。
- 世界观文字太多。

## 9. 首页 UI 简化方案

首页唯一核心目标：让用户 3 秒内知道这是恋爱人格测试，并看到“开启心岛航行”按钮。

### 当前首页主要问题

- 390px 移动端首屏只看到标题和副标题，看不到开始按钮。
- 核心说明位置偏后，首屏信息不足。
- 卖点卡、免责声明、图鉴入口等元素增加了纵向高度。
- 背景氛围有余，但行动引导不足。
- 多入口会稀释“开始测试”这个唯一行动。

### 保留元素

- 小岛/航行符号或轻量 Logo。
- `心岛计划` 标题。
- 一句核心说明。
- `开启心岛航行` 主按钮。
- 简短补充：`36 道题 · 约 5 分钟 · 生成你的心岛人格卡`。

### 下移元素

- 三张卖点卡。
- 完整免责声明。
- 人格图鉴入口。
- 保存上次结果提示。

### 弱化元素

- 复杂背景层。
- 大面积空白。
- 多个次级按钮。
- 长说明文字。

### 首屏布局建议

移动端首屏结构建议：

1. 顶部 10%-15%：小岛符号或轻量 Logo。
2. 中上部：`心岛计划` 标题。
3. 标题下：一句核心说明，例如“探索你在亲密关系里的靠近方式”。
4. 中部：`36 道题 · 约 5 分钟 · 生成你的心岛人格卡`。
5. 中下部：主按钮 `开启心岛航行`。
6. 底部：轻量免责声明或下滑后展示。

### 375/390/430 移动端首屏目标

| 宽度 | 首屏目标 |
| --- | --- |
| 375px | 标题、核心说明、补充信息、主按钮全部可见，按钮不贴底 |
| 390px | 主按钮完整可见，下面可露出少量次级说明 |
| 430px | 首屏可出现一个轻量次级信息，但不影响主按钮 |

首页 v1.0 验收标准：不滚动即可看到 `心岛计划`、一句说明和 `开启心岛航行`。

## 10. 做题页 UI 简化方案

做题页核心目标：让用户顺畅完成 36 题，而不是欣赏复杂场景图。

### 当前做题页问题

- 移动端场景图约占上半屏，题卡被推到下方。
- 题卡中地点、标题、叙事、选项同时出现，信息偏密。
- 36 题长期作答有疲劳风险。
- 场景氛围强，但可能降低作答效率。
- 36 个 prop SVG 仅 4 个存在，说明小装饰系统不完整。

### 推荐信息层级

1. 顶部：`01 / 36`、当前位置、轻量进度条。
2. 氛围：小尺寸场景条或背景氛围，不做大图主视觉。
3. 主体：题目标题和一句叙事。
4. 行动：4 个清晰的大按钮选项。
5. 辅助：上一题。

### 场景图弱化方式

- 从大图主体弱化为顶部氛围条。
- 或作为低透明背景，不挤压题卡。
- 保留地点名和进度节点，让用户仍有航行感。
- prop SVG 缺失不作为 P0，但不要让 fallback 产生视觉噪音。

### 题卡简化方式

- 每题只保留必要叙事，不展示过多地点说明。
- 选项按钮继续保持大点击面积。
- 减少卡片嵌套和过重边框。
- 避免复杂入场动画。
- 上一题保留，但保持次级视觉。

### 移动端作答体验目标

- 用户进入题目后第一眼看到“题目 + 至少 2 个选项”。
- 选项按钮高度不低于 44px。
- 题目切换不打断阅读。
- 36 题过程中始终知道进度。
- 场景存在但不抢主任务。

## 11. 结尾过渡页简化方案

结尾页核心目标：把“答完题”转化成“抵达心岛”。

### 当前结尾页状态

当前已有 `#ending-screen`，包含湖面、光点、小岛浮现、路线、跳过按钮等元素。它已经具备仪式感基础。

### 是否保留

建议保留。结尾过渡是心岛区别于普通测试网页的重要产品记忆点。

### 是否简化

需要简化。结尾页不应加入复杂剧情，也不应让用户等待太久。仪式感服务于结果期待，而不是成为单独动画短片。

### 推荐结构

1. 深海/湖面背景。
2. 星点或光点短暂汇聚。
3. 小岛轮廓浮现。
4. 1-2 句短文案。
5. 自动进入结果页，并保留“直接查看结果”。

推荐文案方向：

- “你的答案正在海面下汇聚。”
- “有一座岛，正在显现。”

动画时长建议控制在 2-3 秒内，超过 3 秒必须有明显跳过入口。

## 12. 结果页 UI 简化方案

结果页是传播核心。首屏只服务一个目标：让用户认领自己的恋爱人格，并愿意保存/分享。

### 当前结果页结构

1. Hero：主人格、匹配度、关键词、命中句、置信说明、分享入口、拟人图。
2. 恋爱人格说明书。
3. 关系惯性折叠区。
4. 关系建议。
5. 展开更多细节。
6. 分享与反馈。

### 当前 Hero 是否足够聚焦

基本合格，但仍偏信息密集。当前 Hero 已经能展示人格名、拟人图、匹配度、关键词和命中句，这是正确方向。问题是置信说明、分享入口和大图同时存在时，移动端首屏视觉重心容易分散。

### 拟人图展示是否需要调整

需要微调，而不是替换。拟人图是传播记忆点，应保留在 Hero，但要避免挤压核心身份信息。移动端可以考虑“上方身份信息 + 中部拟人图 + 下方分享按钮”的清晰顺序。

### 分享入口是否需要强化

需要强化。Hero 中的分享入口目前是轻量文字按钮，视觉权重偏低。v1.0 应把 `生成分享卡` 提升为首屏明确行动之一，但不应与“重新测试”等次级动作并列。

### 应折叠或下移的内容

- 大段最终解读。
- 12 维地图。
- Top5 相近人格。
- 适配关系。
- 旅途回顾。
- 人格图鉴入口。
- 反馈表。
- 本地保存说明。

### 推荐结果页结构

1. Hero 身份卡：人格名、拟人图、匹配度、3 个关键词、命中句、生成分享卡按钮。
2. 简短人格说明：3-5 行内解释“你为什么是这个类型”。
3. 关系惯性分析：折叠展示。
4. 相处建议：短卡片或三条建议。
5. 更多细节折叠：12 维地图、Top5、旅途回顾。
6. 分享与反馈：分享卡预览、保存、反馈、复测。

### 结果页目标形态

结果页应该像“身份卡 + 轻报告”，而不是长报告。用户在首屏完成身份认领，在下滑时获得解释，在最后选择分享、反馈或复测。

## 13. 分享卡简化方案

分享卡是传播核心，不是报告截图。

### 当前分享卡功能状态

当前已有 Canvas 生成逻辑，支持分享卡、长图、保存图片、原生分享和复制分享文字。代码位置在 `app.js` 的分享图模块。

### 当前分享卡视觉风险

- 信息可能偏多，容易变成长报告压缩版。
- 移动端保存依赖浏览器行为，真机风险未完全验证。
- 未看到二维码接入，产品入口提示较弱。
- 人格图加载失败时可能影响分享卡核心视觉。

### 推荐分享卡结构

分享卡只保留：

- 心岛计划 Logo 或文字标识。
- 人格名。
- 拟人图。
- 3 个关键词。
- 一句命中句。
- 简短引导语。
- 产品名 / 测试入口提示。

分享卡不放：

- 大段解释。
- 多个图表。
- 复杂背景。
- 太多装饰。
- 详细分数。
- 过长建议。

### 适合小红书 / 朋友圈传播的视觉目标

- 一眼能看懂“我是什么人格”。
- 拟人图是视觉中心。
- 关键词适合截图阅读。
- 命中句有情绪记忆点。
- 背景克制，有高级感。
- 文字不溢出，不模糊，不像系统报告。

### 是否优先做移动端保存验证

是。分享卡是传播链路核心，v1.0 RC 前必须在移动端浏览器、微信内置浏览器或目标发布环境中验证保存和分享行为。
